# CompLearn accessibility roadmap

CompLearn aims for WCAG 2.2 Level AA across the landing page, workbench, results, and authentication surfaces, with selected Level AAA improvements where they materially help scientific use. This is a delivery target, not a claim of conformance. Conformance requires repeated manual testing with assistive technologies as well as automated checks. The work is divided into reviewable PRs, and the next item starts only after the previous PR receives an explicit approval signal.

## Impact scale and ordering

Impact is scored from 1 to 10 using three considerations: how many users and routes are affected, whether the problem blocks a task or only makes it harder, and how often users encounter it. A score of 10 is a cross-application or results-level blocker; 7 is still valuable but affects a narrower group or can be worked around. Scores express expected user impact, not implementation effort. The sequence also respects dependencies, so a foundational item may precede another item with the same score.

## Audit baseline

The 2026-08-09 source and browser audit found good existing practices: primary landmarks are present, landing-page headings form a coherent hierarchy, major figures and tables have accessible names, controls generally use native buttons and inputs, errors commonly use alert semantics, focus outlines are globally defined, and reduced-motion rules already cover the landing page and selected workbench transitions. The default planar tree is also more accessible than forcing users into a 3D camera.

The main gaps are systemic rather than cosmetic. All routes repeat a sticky header without a bypass mechanism; the static document title does not identify the active route; client-side navigation does not move focus; the sign-in overlay does not initially receive or contain focus; the underlying page remains interactive while the overlay declares itself modal; and the source selector implements only part of the ARIA tabs contract. Several later workflow states rely heavily on spatial or visual presentation, progress updates lack a complete control and announcement strategy, and file ingestion still contains an older drag-and-drop implementation with unnamed icon actions.

## A11Y-01 implementation contract

The first PR establishes a focus and navigation contract shared by every route. Each page exposes one `main-content` target. A keyboard-visible skip link moves both viewport and programmatic focus to that target. Every route supplies a distinct document title, and an in-app route change moves focus and the viewport to the newly rendered main landmark without placing it beneath the sticky header. Initial page load does not steal focus, including when React Strict Mode repeats effects during development.

The sign-in dialog lives outside the inert application shell. Opening it records the invoking control, prevents background interaction and page scrolling, moves focus into the dialog, and contains forward and reverse tab movement. Escape, the close button, or an overlay click closes it; cleanup restores the previous inert and scrolling state and returns focus to the invoker. The overlay acts on `click`, rather than pointer-down, so users can cancel an accidental press by moving away before release.

Tests cover initial-focus preservation, bypass focus, route title and focus behavior, modal entry, forward and reverse focus containment, Escape, background inertness, scroll locking, focus restoration, and an axe-core WCAG A/AA scan of the landing route. Axe's color-contrast rule is disabled only in JSDOM because that environment has no layout engine; color and non-text contrast remain explicit browser/manual work in A11Y-06.

## Verification policy for subsequent PRs

Every accessibility PR must include focused automated tests, full relevant regression tests, type/lint/build checks with pre-existing failures distinguished from regressions, browser verification at keyboard-only and 200% zoom where relevant, and a timestamped update to this roadmap. Automated checks are a guardrail, not the acceptance decision. Components with custom keyboard behavior, live regions, canvas, WebGL, drag-and-drop, or focus management require manual behavior verification before their item is marked complete.

Primary references are [WCAG 2.2](https://www.w3.org/TR/WCAG22/), the [WAI-ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/), and the [axe-core documentation](https://github.com/dequelabs/axe-core). Product-specific decisions should preserve CompLearn's end-user UI policy and scientific reproducibility contracts.
